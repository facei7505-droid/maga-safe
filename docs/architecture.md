# ПРУФ: архитектура

**Идея.** Мошенники меняют слова, но переиспользуют «пруфы»: скриншоты выплат, голосовые, тексты-шаблоны, номера Kaspi, домены. ПРУФ ищет признаки схем в каждом сообщении и связывает сообщения через повторно использованные артефакты в кейсы и семейства кампаний. Система показывает **признаки**, а не вердикты; решение принимает аналитик.

Одна платформа на три трека: платные розыгрыши (`lottery`), скрытая реклама казино (`casino`), пирамиды с переводами Kaspi (`pyramid`).

## Поток данных

```
источник (API / дашборд / Telegram-бот / пакетный импорт)
   │
   ▼
1. Приём: Submission {text?, images[], audio?, links[], source, channel, posted_at}
   │
   ▼
2. Нормализация (pruf/normalize)
   - текст: NFKC, гомоглифы, leet (0→о, 3→з), транслит lat→кир для ru/kk, сленг-словарь
   - изображения: OCR (RapidOCR = PP-OCR в ONNX) → текст + токены с координатами
   - аудио: Whisper-адаптер (faster-whisper, если доступна модель) → текст
   - ссылки: канонизация URL, раскрытие сокращателей, извлечение домена
   - реквизиты: телефоны +7, карты (Luhn, маскирование), IBAN KZ, kaspi.me/pay-ссылки
   │
   ▼
3. Детектор сигналов (pruf/detect)
   - правила: словари признаков по трекам с весами, цитата и позиция для каждого срабатывания
   - обязательные сочетания (например, «выигрыш» без «взноса» не даёт высокий риск)
   - стоп-признаки легальности: «без взноса», официальные правила, allowlist брендов
   - ML: char n-gram TF-IDF + логистическая регрессия по трекам (обучение на синтетике и ручных dev-наборах)
   - LLM (Claude): только для спорной зоны (балл 20–74), строгий JSON с цитатами; без ключа отключён.
     Цитаты LLM, которых нет в тексте, отбрасываются; «легальный контекст» от LLM опускает балл до низкого только у поста без ссылок, реквизитов, контактов и просьб о деньгах; кэш и дневной бюджет вызовов
     (защита от prompt injection в самом посте), текст обёрнут в тег со случайным nonce
   │
   ▼
4. Реестр ПРУФ (pruf/registry)
   - изображения: PDQ (256 бит), векторный перебор по Хэммингу (numpy bitwise_count):
     близкая копия ≤ 40 бит; при обрезке и подписи канала до 96 бит, если совпадают «сильные»
     токены OCR (номер квитанции, дата, время); разные чеки одного шаблона (тот же банк,
     другие номер и дата) копией не считаются
   - тексты: MinHash (64 перестановки) + LSH (16 полос × 4) по шинглам нормализованного текста
   - реквизиты и домены: точный индекс по нормализованному ключу (карты по HMAC)
   - OCR-дифф копий: выравнивание токенов с поправкой на обрезку, склейка по-разному
     разрезанных строк, подсветка изменённых сумм и дат (только если цифры есть в обеих версиях)
   - криминалистика правок: ELA в зоне цифр (слабый сигнал, вес 8)
   │
   ▼
5. Граф (pruf/graph): NetworkX для MVP, схема совместима с Neo4j
   узлы: post, channel, requisite, proof(image|text), domain; рёбра: posted_in, mentions, reuses, links_to
   кейс = компонента связности рискованных постов (средний и высокий риск); низкие посты
   прикрепляются как контекст, но кейсы не склеивают. «Хабы» (реквизит или домен больше чем
   в 50 постах, или 70%+ низких постов среди 5+) рёбер не дают. Номер кейса стабилен, если
   у кейса уже есть статус аналитика. Семейство кампании = кластер по общим пруфам
   │
   ▼
6. Скоринг (pruf/scoring): балл 0–100 = признаки текста + ML + сигналы реестра + граф
   уровни: низкий < 35 ≤ средний < 65 ≤ высокий; каждый вклад с объяснением
   │
   ▼
7. Выход
   - дашборд аналитика: очередь кейсов по риску, карточка кейса, дифф пруфов, «найти связанные», таймлайн появлений
   - пакет доказательств: ZIP (артефакты, manifest.json с SHA-256 и UTC-временем, report.html, граф)
   - API для банков: лента засвеченных реквизитов с уровнем риска и числом кейсов
   - Telegram-бот: пользователь пересылает скрин/ссылку, получает признаки и риск
```

## Правило «повтор сам по себе не риск»

Повторно использованный скриншот или текст повышает балл, только если в связанных постах уже есть признаки схемы или есть признаки правки (отличаются суммы при совпадении остального, аномалия ELA). Бренды из allowlist (Kaspi, Halyk, официальные лотереи) не дают сигнал «повтор логотипа». Легальные конкурсы без взноса и с правилами получают стоп-признак.

## Деградация видна, а не скрыта

Если OCR, Whisper или LLM недоступны, анализ идёт по остальным сигналам, а в ответе есть поле
`degraded` с причиной; `/api/v1/stats` отдаёт `capabilities`, дашборд показывает баннер.
Пост, на котором приём упал, получает статус `failed` и не попадает в граф.

## Telegram-бот

`pruf/bot/telegram.py`: long polling (`python -m pruf.bot.telegram`) или webhook
`/api/v1/telegram/webhook` с секретом в заголовке `X-Telegram-Bot-Api-Secret-Token`.
Бот вызывает `Pruf.check(public=True)`: реестр и граф только читаются, сообщения пользователей не
сохраняются. Человек видит, что номер или скрин уже встречались в постах с признаками схем и что на
копиях менялись суммы, но не видит каналов, сумм с чужих скринов, счётчиков и треков: бот не должен
становиться справочником по базе для мошенников. Отвечает только в личных чатах. Лимиты: 20 сообщений
в минуту на чат и 120 на всех, файлы до 8 МБ с проверкой сигнатуры, голосовые до 2 минут.
Вебхук проверяет секрет (не короче 32 символов) до чтения тела, тело до 1 МБ, повторные доставки
отбрасываются по `update_id`, обработка идёт в отдельном пуле из 2 потоков с очередью до 50 задач,
поэтому OCR и Whisper не занимают потоки API.

## Масштабирование (замер `scripts/loadtest.py`, 1 CPU-поток)

| Индекс | 1 млн элементов | Память | Запрос p50 / p99 | Полнота |
|---|---|---|---|---|
| PDQ, перебор по Хэммингу, порог 96 | загрузка 0,3 с | 31 МБ | 32 / 46 мс | 100% копий с 8–40 изменёнными битами |
| MinHash LSH 16×4 | загрузка 10 с | ~1 ГБ (с запасом ёмкости) | 0,1 / 0,4 мс | 100% при сходстве ≥0,7; 92% при 0,6 |

- Дозапись одного текста в среднем мгновенна, раз в 4096 элементов буфер сливается (до ~75 мс).
- Перебор PDQ линеен: при 10 млн это ~0,3 с на запрос, дальше нужен Multi-Index Hashing или FAISS
  binary index; MinHash-сигнатуры можно хранить в uint32 и шардировать.
- Для пилота: Postgres вместо SQLite, объектное хранилище для blob, Neo4j для графа, очередь
  (Redis/RQ) для OCR и Whisper. Интерфейсы репозиториев уже отделены. Сейчас индексы живут в
  памяти одного процесса, поэтому сервер запускается с одним воркером (проверяется при старте).

## Пропускная способность (замер `scripts/throughput.py`, один процесс, без OCR и LLM)

| Что | Результат |
|---|---|
| Приём поста целиком: нормализация, правила + ML, реестр картинок и текстов, реквизиты, SQLite | 2000 постов (18% с картинкой) за 48 с: **~2 500 постов в минуту**, p50 22 мс, p95 48 мс |
| Сборка графа кейсов по всей базе | 0,9 с |
| `POST /api/v1/bank/check` (банк проверяет номер) | p50 6 мс, p95 8 мс |
| `POST /api/v1/inspect` (расширение) | p50 5 мс, p95 7 мс |

- Оценка для Казахстана: 5 000 каналов × 20 постов в день = 100 тыс. постов в день ≈ 70 в минуту.
  Один сервер держит поток с запасом ~35 раз. OCR картинок и Claude в спорной зоне идут отдельной
  очередью и в этот замер не входят.
- Внедрение по шагам: пилот с одним банком и аналитиком (серый список CSV раз в день) → вебхук
  в антифрод банка и чёрный список после проверки человеком → обмен через Антифрод-центр Нацбанка
  (формат выгрузки `/api/v1/bank/requisites.csv`: HMAC-ссылка ключом обмена, маска, статус, срок, основание).

## Списки для банков

- **Серый**: номер в постах среднего или высокого риска, кейс не проверен. Совет: проверить перевод.
  Срок проверки 3 рабочих дня с первого такого поста; просроченные поднимаются наверх на сайте.
- **Чёрный**: аналитик подтвердил кейс. Совет: приостановить перевод до проверки. Расширение при
  копировании такого номера показывает «в чёрном списке».
- **Снят**: аналитик отклонил кейс. Совет: не блокировать; расширение такой номер не помечает.
- Решение хранится на реквизите (`requisite_status`), а не на кейсе: оно переживает пересборку графа.
  Чёрный побеждает снятый. В списки идут только номера из постов среднего и высокого риска кейса.

## Безопасность и данные

- Только открытые или синтетические данные. Номера карт маскируются (первые 6 и последние 4) до записи
  в базу, экспорта и отправки в LLM; для сопоставления хранится HMAC-ключ (`PRUF_HMAC_KEY`,
  в режиме разработки случайный ключ в каталоге данных). Банковская лента не отдаёт ключи сопоставления.
- Доступ к API по именованным токенам из переменных окружения (`PRUF_ANALYST_TOKEN`, `PRUF_BANK_TOKENS`),
  лимит запросов (неудачные попытки считаются по IP), лимит размера тела, проверка сигнатуры файла,
  защита от «бомб» распаковки, CSP и заголовки безопасности, аудит экспорта и смены статусов.
- Раскрытие сокращённых ссылок выключено по умолчанию и не ходит на внутренние адреса (SSRF).
- LLM получает текст поста с замаскированными картами. Телефоны и ссылки в посте остаются: это
  признаки схемы. Данные пользователя бота (кто прислал) в LLM не передаются.

## Агент-Разведчик и расширение

```
семена (реестр / --seed) ─▶ приоритетная очередь ─▶ источник (Telethon только чтение | фикстура)
                                 ▲                         │ карточка канала, посты, поиск
                                 │                         ▼
     ссылки t.me, репосты, @упоминания,          детектор ПРУФ → реестр (source=scout)
     поиск по номерам Kaspi, IBAN, доменам ◀──── риск канала ≥ 65? → идём дальше
```

- `pruf/scout/`: движок (`scout.py`), источники (`sources.py`: фикстура и ограничитель запросов, `telegram.py`:
  Telethon за белым списком методов чтения), CLI `python -m pruf.scout`. Каналы и связи лежат в таблицах
  `scout_channels` и `scout_edges`; посты разведчика проходят обычный приём и попадают в кейсы.
- `pruf/inspect.py` + `extension/`: расширение считает признаки локально и отправляет на `POST /api/v1/inspect`
  только реквизиты, ссылки, хэш текста и номера признаков. Сервер добавляет то, что знает реестр: засвеченный
  реквизит, домен из чёрного списка (`GET /api/v1/blacklist/domains`, домены постов высокого риска без брендов и
  мессенджеров), точную копию рискованного текста. Отдельный токен `PRUF_EXTENSION_TOKENS` не даёт доступа к кейсам.
